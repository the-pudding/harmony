# Section key review

You are reviewing **individual sections** of songs whose local chord content suggests a different key or mode than the song's overall label. The queue was generated by a Viterbi section-key detector that found at least one section fitting another tonal centre better than the song's primary key.

## Input

A queue batch in `harmony-data/data/key-review-section-queue/batch-*.json`. Each entry has:

- `songKey`, `title`, `artist`, `source`, `url` — song metadata
- `songLabeledKey` — the song's current global key (after any song-level ledger correction)
- `sections` — every section's `sectionId`, `name`, `labeledKey` (same as song global for UG songs), `chords`, `romans`, `chordCount`
- `flags` — sections the detector suspects need a different key: `sectionId`, `kind` (`modulation`, `relative`, `mode`), `suggestedKey`, `margin` (confidence)

## Output

Write `harmony-data/data/key-review-section-decisions/<same file name as your queue batch>` containing one entry per song, in the same order:

```json
[
  {
    "songKey": "artist__song",
    "sections": [
      {
        "sectionId": "artist__song__ug-chorus-0",
        "labeled": "Eb major",
        "verdict": "corrected",
        "key": "G",
        "scale": "major",
        "confidence": "high",
        "note": "Chorus centres on G–C–D–G; Eb major reads this as III–VI–VII which is clearly wrong."
      }
    ]
  }
]
```

Write an entry for **every song** in the batch. For each song, write a `sections` array with a decision for **every flagged section** (even when confirming it). This suppresses the section from appearing in the next queue run. Songs with no corrections still need an entry with all-confirmed sections. Include a `song` field only when the global key itself is wrong (see below).

## Deciding whether a section needs its own key

For each flagged section, inspect its chords vs the song's global key and vs the `suggestedKey`:

### 1. True modulation (`kind: "modulation"`)

The section uses a pitch collection that differs from the song's global key (e.g., song is Eb major, chorus uses G–C–D–G which is G major).

- **Correct**: set `key` and `scale` to the section's actual tonal centre.
- **Not correct**: section chords are borrowed (e.g., a IV→♭VII→I passing through a parallel major) or a single chromatic chord.
- Use the web (chords sites, music databases) if the chord names look transposition-suspect.

### 2. Relative major/minor (`kind: "relative"`)

The section centres on the relative minor (or major) of the song key. E.g., a verse labelled C major that really resolves to Am.

- Evidence: the section begins and ends on Am; strong E major (V of Am) cadences.
- Ambiguity: pure IV–vi–I–V progressions often feel equally at home in both keys. Use `confidence: "medium"` and leave the song key if you are unsure.

### 3. Mode shift (`kind: "mode"`)

Same tonic, different mode. E.g., a chorus in G major vs a verse in G mixolydian.

- Mixolydian: ♭VII prominent, major V rare or absent.
- Dorian: minor i is home, major IV prominent.
- These are subtle; `confidence: "medium"` or `"low"` is appropriate.

## When the song-level label is wrong

If the song's global key itself is wrong (e.g., Honeydrippers `sea-of-love` was set to F# mixolydian when it is G major), add a `song` field to revise the main ledger row:

```json
{
  "songKey": "the-honeydrippers__sea-of-love",
  "song": {
    "verdict": "corrected",
    "key": "G",
    "scale": "major",
    "confidence": "high",
    "note": "Song is clearly G major; the F# mixolydian label is a detector error."
  },
  "sections": [...]
}
```

The `song.key` follows the same rules as the song-level review: use the chord key as listed, with optional `recordedKey` for capo/transposition cases.

## Scrape garbage → problematicSongs

If a flagged section is detected as a different key only because the scrape itself is broken (e.g., the Blackbyrds interlude which isn't in the actual song), do **not** label it with a section key. Instead, write a `"note"` explaining it and `"verdict": "confirmed"` for those sections, so they are suppressed from future queues. Add the song to `problematicSongs` in `hand-reviewed-songs.ts` with a note.

## Key choices

- `key`: the tonic note of the chords **exactly as listed** (same rule as song-level review).
- `scale`: one of `major`, `minor`, `mixolydian`, `dorian`. Rare modes only with a `note` justification.
- `recordedKey` (optional): real recording pitch, for capo-shifted sections (like We Five where the written chords are a semitone flat of the actual recording).
- `confidence`: `high`, `medium`, or `low`.
- `verdict`: `confirmed` (section key is fine as labeled) or `corrected` (use your `key`/`scale`).

## Section IDs

The `sectionId` in your decision must exactly match the `sectionId` from the queue entry. Do not invent new IDs.

## Rules

- Provide a decision for every song that appears in your batch.
- Provide a `sections` entry for every **flagged** section (from the `flags` array) for every song — even when confirming it. This suppresses it from the next queue run.
- You do NOT need to write entries for non-flagged sections.
- Check that your output is valid JSON.
- Do not edit other files.
